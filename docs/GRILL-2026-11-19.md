# Гриллинг DRAFT-REVIEW — решения владельца (2026-11-19)

Ответы владельца на «Decisions taken by agents» (1–13) и «Open questions» (O1–O10) из
`docs/DRAFT-REVIEW.md`. Это входные данные для следующей итерации. Где решение расходится
с наброском, нужно менять PROTOCOL, ADR, contracts и код.

## Сквозной принцип

**Всё настраиваемо.** По умолчанию безопасно, но если владелец явно хочет ослабить защиту
ради удобства, мы ему не мешаем: «стрелять себе в ногу можно». Ослабление делается только
через consent, сам агент ослабить ничего не может. Исключение — уровень Never (см. O9): он
снимается только в настройках.

## Решения по пунктам агентов

**1. Подпись мандата.** Подписывает гейт ключом арендатора, ADR 0012 остаётся как есть.
Подпись самого владельца и биометрия (A2+/A3) отложены, вернёмся позже. Поля
`attestation`/`owner_sig` сейчас не вводим.

**2. Ключи.** Один Ed25519 на арендатора, назначения разделяются JWS `typ`. **В MVP
обязателен готовый алгоритм ротации:** новый ключ подписывается старым, пиры принимают его
автоматически, старый работает ещё N дней.

**2a. Адрес не равен ключу (изменение).** Адрес — это постоянный id арендатора `t_…`, он
никогда не меняется. Пир хранит запись «у `t_x` текущий ключ K2, K1 действует до даты».
Ротация обновляет эту запись сообщением, подписанным старым ключом. В наброске сейчас
key id = адрес, это нужно переделать.

**3. Release digest.** Состав прежний: арендатор, пир, нить, `in_reply_to`, хеш содержимого,
метаданные вложений. Изменения: вместо key ids в дайджест идут постоянные адреса `t_…` обеих
сторон, и в него добавляется срок жизни черновика (`expires`). Этот срок настраивает владелец.

**4. Входы агентских инструментов.** Строгие: неизвестное поле даёт `invalid_input`. Остальные
читатели терпимые, но поля, несущие полномочия, строгие. Без изменений.

**5. Шаблоны и полки (закрывает O7).** По умолчанию T0, то есть нужен A1. Это настраивается.
При знакомстве с пиром показывается одна кнопка «шаблоны и полка "для друзей" без спроса»,
которая выдаёт открытый мандат T1 одним тапом.

**6. Время жизни closed mandate.** Получатель отклоняет мандат, если `exp − iat > 60 s`. Это
дефолт, получатель может ослабить его для конкретного пира. При ретраях мандат
перевыпускается со свежим временем без повторного вопроса владельцу, но только пока жив
черновик.

**7. Высокий риск без A2+/A3 (изменение, закрывает O5).** Такие черновики **не блокируются**.
Требуется самая сильная защита из доступных на данный момент. В MVP вместо биометрии
вводится ступень A2+ = Mini App + PIN/пароль.

**7a. PIN/пароль.**
- Вводится только в Mini App, никогда в чате.
- В гейте хранится только хеш Argon2id.
- Задаётся на церемонии первого запуска. Сменить можно через consent со старым PIN, а также
  локальным CLI на сервере.
- После 5 неверных попыток подряд — заморозка на 15 минут и уведомление владельцу.
- По умолчанию PIN из 6 цифр, можно выбрать полноценный пароль.
- В THREAT-MODEL честно пишем: от оператора хостинга это не защищает, потому что код
  Mini App отдаёт он.
- Когда появится биометрия, PIN останется запасным способом.

**8. Канарейка.** Черновик блокируется, арендатор переходит в tripwire. В этом режиме все
открытые мандаты останавливаются, а каждый черновик требует самую сильную доступную защиту
(A2 + PIN). Снять режим можно через consent с PIN. В уведомлении сразу есть контекст: пир,
черновик, журнал MCP. Режим можно ослабить (например, «только блок черновика»), но по
умолчанию тревога полная.

**9. Доверие «на разговор».** Это открытый мандат на одну нить. Нить — цепочка `in_reply_to`,
как в почте; сообщение без `in_reply_to` открывает новую нить. Длительность настраивается.
Под черновиком кнопка «Отправить и дальше в этой нити без спроса N мин», нить называется по
первому сообщению. **Агентам это объясняем явно** в трёх местах:
- в описании `propose`;
- в AGENT-SETUP и скилле connect;
- в ответах `propose`/`inbox`: действует ли в нити мандат, сколько осталось, и что новая
  нить пойдёт через владельца.

**10. Знакомство (pairing).**
1. Пригласительная ссылка.
2. Приглашённый открывает её у своего гейта.
3. Оба подтверждают на A2.
4. SAS из 6 цифр формально опционален, но предлагается по умолчанию, пропустить можно
   одним тапом.

Если сверку пропустили, пир помечается «не сверено», и уровни выше T1 для него требуют
сверку. Владелец может отключить это требование.

**11. Значения по умолчанию.**

| Параметр | Значение |
|---|---|
| срок жизни черновика | **12 ч** (настройка от 5 мин до 7 дней) |
| окно `initData` | 300 s |
| closed mandate | 60 s |
| окно конверта | 7 дней |
| горизонт ретраев | 72 ч |
| черновиков от агента на пира в час | 30 |
| ожидающих черновиков на арендатора | **50** |
| доверие «на разговор» | **30 мин, без лимита сообщений** (сверху ограничивает 30/пир/час) |

**12. Ход пира (ADR 0011).** Это **рекомендация, а не протокол**: гейт не может проверить, как
устроен агент. Риск несёт владелец того агента, который читает входящее. Уровни защиты:
- **L3** — ограничения ОС: отдельный unix-пользователь, сеть только до модели и до гейта.
  Работает для любого агента. Нужность подтверждена кейсом DTEX: Hermes вынес данные через
  gofile.io в обход Telegram.
- **L2** — отдельный прогон через `paseka peer-turn`. Подходит любому CLI-агенту; где агент
  умеет, прогон стартует с форком основной сессии, чтобы был полный контекст.
- **L1** — риск принимается осознанно.

Скилл connect спрашивает уровень и записывает его. Гейт всегда показывает владельцу этот
уровень, а для L1 держит постоянную пометку «входящее от пиров читается без защиты».

**13. Нумерация CA.** Только дописывается в конец, CA-47 сохраняется. Принято.

## Открытые вопросы

**O1.** Получатель в MVP верит заявке гейта отправителя об A1/A2 (следует из решения 1).

**O2. Скилл установки.** Исходник лежит в репо для ревью, а релиз — отдельный подписанный
артефакт. Его хеш публикуется минимум в двух местах: README организации, GitHub release,
канал владельца. Первым шагом скилл сверяет собственный хеш с этими местами; если они
расходятся — стоп и тревога.

**O3. Бот согласия.**
- Self-host: у каждого свой бот.
- Хостинг: один общий бот, арендатор определяется строго по подписанному Telegram id (TI-5,
  CA-39). По желанию можно подключить своего бота: это даёт изоляцию и задел на переезд в
  self-host.

**O4. Ключи Telegram Ed25519.**
- До M3 сверить ключи prod и test с документацией и добавить пример `initData` из
  документации Telegram как тестовый вектор.
- Живая проверка на церемонии первого запуска: установка не завершится без валидной подписи.
- Ключи хранятся в конфиге. Менять их можно через consent или локальным CLI, иначе получается
  круг: проверка consent сама зависит от этого ключа.

**O5** закрыт решением 7, **O6** — решением 11 (12 ч), **O7** — решением 5.

**O8. Имена в CLI.** `paseka init` спрашивает локальное имя и сопоставляет его с `t_…`. В CLI
используется только это имя; при одном арендаторе `--tenant` не нужен. Имя локальное, пиры
его не видят.

**O9. Чувствительные данные (расширено).** Вместо «папок» вводим **реестр источников**:

| Источник | Способ ловли |
|---|---|
| файлы и папки | отпечатки |
| память, скиллы, CLAUDE.md, системный промпт агента | отпечатки; подключаются по умолчанию при connect |
| секреты | правила в духе gitleaks + энтропия |
| именованные секреты из хранилища | точное совпадение значений |
| приватные ссылки (Docs «по ссылке», подписанные S3, инвайты, magic-link) | домены + токены в query |
| MCP-источники (почта, календарь, контакты) | taint по журналу источников |
| входящие от пиров | автоматический отпечаток, утечка от одного пира к другому |
| другие чаты и группы | содержимое группы X чувствительно для всех, кто не состоит в X |
| память о третьих лицах | тег |
| персональные идентификаторы (телефон, адрес, карта/Luhn, IBAN, координаты) | валидаторы |
| одноразовые коды, 2FA, OTP | **Never** |
| картинки | удалять EXIF сразу; OCR позже |

**UX для владельца:** Allow / Ask / Never для каждой пары «источник × пир». Идея взята из
Telegram Dictator for macOS (macos-beta.telegram.org/dictator). Под Ask гейт сам выбирает
канал подтверждения по уровню риска. Never снимается только в настройках.

В MVP отпечатки — точные кусочки. MinHash, OCR и LLM-проверка добавятся позже как новые
детекторы того же реестра.

**O10.** Упоминание `vladmesh/agent-peer-protocol` в CONCEPT.md оставляем, но оформляем ссылкой
в разделе «История»: «вырос из agent-peer-protocol, несовместим намеренно (ADR 0009)».
Больше нигде старый репо не упоминается.

## После MVP (в концепцию)

- Подключаемые методы аутентификации (PIN/пароль, биометрия, passkey, TOTP…) с гибкой
  настройкой: какой метод для какого уровня, пира или ситуации.
- Подпись владельца (`owner`-attestation) для A2+/A3.
- MinHash, OCR, LLM-детектор пересказа.

## Что менять в наброске

1. Ротация ключей и разделение адреса и ключа: PROTOCOL, contracts, `paseka-proto`/`-core`,
   новые CA.
2. В release digest — адреса `t_…` и `expires`; перегенерировать векторы.
3. Убрать блок `policy` для A2+/A3. Добавить ступень A2+PIN (Argon2id, лимит попыток,
   церемония).
4. В tripwire требовать A2+PIN; снятие с PIN.
5. Новые дефолты (12 ч, 50 pending, разговор 30 мин без лимита сообщений).
6. Нити в описаниях инструментов и в ответах `propose`/`inbox`.
7. Пометка «не сверено» при pairing и требование сверки для уровней выше T1.
8. Реестр источников с Allow/Ask/Never, новые детекторы (OTP, именованные секреты, ссылки,
   чаты/группы), удаление EXIF.
9. ADR 0011: перевести в статус рекомендации, описать уровни L1–L3 и пометку для L1.
10. Скилл установки: подписанный релиз и самопроверка хеша.
11. Ключи Telegram в конфиге и живая проверка на церемонии.
12. Локальные имена арендаторов в CLI.
13. CONCEPT.md: раздел «История».
